# Quantum-Safe Security of Multimedia Traffic in 6G Networks

Experiments for the project **"Quantum Computing Based Security of Multimedia Traffic in 6G Networks"**, 
Firas Ftoutou: 2nd-year Research Master’s in Intelligent Systems for Imaging and Artificial Vision, Higher Institute of Computer Science - Ariana, University of Tunis El Manar
Course: *Sharing Multimedia Content* : Prof. Rachid Zagrouba 

## Idea

Quantum computers threaten the **key exchange** of a video session (RSA, elliptic curves — Shor's algorithm), not the **encryption of the video itself** (AES-256 stays safe against Grover's algorithm).

The proposed approach has three simple steps:

1. **Hybrid key exchange:** X25519 + ML-KEM-768 (NIST FIPS 203), signed with ML-DSA-44 (NIST FIPS 204).
2. **Video encryption:** AES-256-GCM on every packet.
3. **Key-change rule:** change the key every `T` seconds, with `T ≥ 8·B / (0.01·R)`, so that the extra traffic stays below 1 %
   (`B` = bytes of one key change, `R` = video bit rate).

A simulation of the **BB84** quantum key distribution protocol shows how a spy is detected.

## What the code measures

| Section | Experiment |
|---|---|
| 1 | Time and size of one key exchange: X25519, RSA-3072, ML-KEM-768, hybrid |
| 2 | Time and size of one signature: Ed25519 vs ML-DSA-44 |
| 3 | AES-256-GCM encryption of a real H.264 video (1080p, 8 Mb/s, 20 s, 1200-byte packets) |
| 4 | Extra traffic of the key-change rule for HD, 4K, XR and hologram streams |
| 5 | BB84 simulation (200 000 photons), with and without a spy |

No external dataset is needed: all data (keys, messages, test video, photons) is generated by the code.

## Main results

Measured with Python 3 on one core of a cloud machine (Intel Xeon, 2.1 GHz), median of 1000 runs.

| Measure | Result |
|---|---|
| Key exchange | ML-KEM-768: 37.3 µs vs X25519: 102.7 µs — but 2272 bytes vs 64 bytes |
| Signature | ML-DSA-44: 56.7 µs vs Ed25519: 110.4 µs — but 2420 bytes vs 64 bytes |
| One post-quantum key change | ≈ 0.2 ms and 4756 bytes |
| AES-256-GCM | 13.6 Gb/s (the HD video needs only 0.008 Gb/s); 28 extra bytes per packet (2.33 %) |
| Key-change rule, HD video (8 Mb/s) | T ≥ 0.48 s keeps the extra traffic below 1 % |
| BB84, no spy | error rate = channel noise (1 % or 5 %) → key accepted |
| BB84, spy (measure and resend) | error rate ≈ 25.5 % → spy detected |

**Conclusion:** for video, the cost of quantum safety is mainly the **size of the messages**, not the computation time.

## How to run

### Option 1 — Google Colab (easiest)

Open `quantumsafe_6g_experiments.ipynb` in Google Colab, then **Runtime → Run all**.
The first cell installs the libraries (about 3–5 minutes).

### Option 2 — Python script

```bash
pip install -r requirements.txt
# ffmpeg is needed for section 3 only: sudo apt install ffmpeg  (or brew install ffmpeg)

python quantumsafe_6g_experiments.py              # run everything
python quantumsafe_6g_experiments.py --section 5  # run one section only
python quantumsafe_6g_experiments.py --runs 200   # fewer timing runs (faster)
```

The first `import oqs` downloads and builds liboqs, which can take a few minutes.

## Libraries

- [cryptography](https://cryptography.io) — X25519, RSA, Ed25519, AES-GCM, HKDF
- [liboqs-python](https://github.com/open-quantum-safe/liboqs-python) (Open Quantum Safe) — ML-KEM, ML-DSA
- [NumPy](https://numpy.org) — BB84 simulation
- [FFmpeg](https://ffmpeg.org) — test video

## Limitations

Tests ran in Python on a cloud computer, without network simulation (delay, packet loss). Results on phones may differ, and the 6G bit rates are example values.
